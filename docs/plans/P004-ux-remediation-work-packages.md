## 1. Overview

This document establishes the phased engineering remediation work packages (WP-13 through WP-20) following the 2026-11-06 UX specification audit, incorporating all owner decisions from Section 8 and the owner-approved UI Contract Amendment (§1.1).

### 1.1 Amendment — Owner-Approved Admin UI Contract (`D-UI-1` to `D-UI-6`, `D-CONTRACT-1` to `D-CONTRACT-7`, `D-WORKSPACE`, `D-EDITOR`, `D-FEEDBACK`, `D-HELP`, and `D-ORDER`)

The following owner-approved architectural decisions govern all admin UI implementation from **WP-15** onward:

#### Editor & Interaction Rules (`D-UI-1` to `D-UI-6`)
- **`D-UI-1` (Single Primary Action, State-Driven Visibility & Focused Editor Width):** One primary action per area and state; actions that depend on state (`Publish`, `Unpublish`, `Delete`, `Unlist`) are shown or hidden by state with no duplicate actions; in the editor, writing uses a centered single-column canvas (`65ch–75ch` max width) with metadata (`Slug`, `Tags`, `Visibility`, `Updated`, `History`) collapsed into a disclosure/drawer rather than a permanent wide form stack.
- **`D-UI-2` (Single Feedback Channel per Result & Clean Action Bar):** One feedback channel per result: a persistent inline status region (`StatusLine`) beside the action is the record (`aria-live="polite"`). Only two persistent primary controls appear in the editor header (`Save draft` and `Publish…` when draft; `Save changes` and `Make public…` when unlisted; `Save changes` and `Visibility ▾` / `More ▾` when published), with `Make private / Unpublish`, `Delete`, and `History` in a `"More"` menu.
- **`D-UI-3` (Authentic Undo & Single Publish Path):** Every transition to `Public` goes through the pre-flight dialog (`#btn-open-publish-dialog`) and requires a passing private-detail scan on both client and server (`UX-57`); `Undo` appears only where it works, in one place (inside the action status line), with a real 1-second countdown and real state/revision restoration (`UX-04`).
- **`D-UI-4` (Plain Owner-Facing Words & Dynamic Pre-Flight Step Numbering):** Owner-facing text uses plain words only: no internal levels (`L0`), pipeline terms (`Enrichment pipeline queued`), or engineering counts (`N revisions purged`); pre-flight dialog steps number dynamically (`1, 2, 3` when clean; `1, 2, 3, 4` when NDA/sensitive review is shown; `UX-58`).
- **`D-UI-5` (Shared Building Blocks in One Place, Zero Inline Styles & Single Live Region):** Shared building blocks (`Button` with `primary`/`secondary`/`danger`/`quiet`, `IconButton` with a label, `StatusLine`, `Dialog`, `Field`) live in one place; pages compose them, with no inline styles and no per-page copies; `#editor-status-line` (`role="status"`, `aria-live="polite"`) is the sole action status line in the editor (`UX-56`, `UX-60`).
- **`D-UI-6` (Isolated Per-Page Modules with Behavioural & Visual Checks):** Each admin page is its own module (markup, behaviour, strings) with its own behavioural test and a visual check; no page reaches into another page's code.

#### Cross-Page Admin Contract Rules (`D-CONTRACT-1` to `D-CONTRACT-7`)
- **`D-CONTRACT-1`:** Owner-facing text uses plain words only: no internal levels (`L0`), pipeline terms or engineering counts.
- **`D-CONTRACT-2`:** Shared building blocks in one place (`Button` primary/secondary/danger/quiet, icon button with a label, `StatusLine`, `Dialog`, form field); pages compose them, no inline styles, no per-page copies.
- **`D-CONTRACT-3`:** Each admin page is its own module (markup, behaviour, strings) with its own behavioural test; no page reaches into another page's code.
- **`D-CONTRACT-4`:** Pages that have no inline status region show a persistent, dismissible notice, never a timed toast.
- **`D-CONTRACT-5`:** A control that cannot work is not rendered.
- **`D-CONTRACT-6`:** A control that cannot work is not rendered.
- **`D-CONTRACT-7`:** Pages without an inline status area use a persistent dismissible notice, never a timed toast.

#### Owner-Approved Workspace, Editor, Feedback & Help Decisions (`D-WORKSPACE`, `D-EDITOR`, `D-FEEDBACK`, `D-HELP`)
- **`D-WORKSPACE`:** The editor screen contains only the entry list, the editor and an optional structure panel. Site-wide actions move to Home and Maintenance; `"Publish Now"` is renamed `"Update public site"`; Inbox and Conflicts appear only on their own screens and show an empty state only there. The admin has its own slim header (product name, section navigation, Sign out, theme toggle) and never renders the public site's navigation or footer.
- **`D-EDITOR`:** Title and body are always visible. Slug, Role profile, Visibility, Date and Temporal confidence collapse into one `"Details"` disclosure with a one-line summary (for example `"Unlisted · 13 Nov 2026 · Exact"`). Actions by state: Draft: `Save draft` + `Publish...`; Unlisted: `Save changes` + `Make public...`; Public: `Save changes` + `Visibility` menu; everything else (`Make private / Unpublish`, `Delete`, `History`) in a `"More"` menu, with `Delete` last and separated. Visibility has one control only (a menu: `Public / Unlisted / Private`); any change to `Public` goes through the Publish pre-flight. The NDA confirmation, the private-details check and its result live only in the `Publish...` dialog; the signed preview token is never shown. The structure panel is hidden until opened from a `"Structure"` button and contains no developer copy. Modes become a segmented control with a selected state, or move into the New entry chooser.
- **`D-EDITOR-2` (Owner Design Corrections, applied in `WP-15.4`):**
  - **(a) One visibility control:** Public and unlisted entries: action bar is `Save changes` + `Visibility` menu (options `Public`, `Unlisted`, `Private`; the current one marked; choosing `Public` from `Unlisted` or `Private` opens the Publish dialog). Draft: `Save draft` + `Publish...`. The `More` menu contains only `History` and `Delete entry...`; it never holds visibility actions. Remove `"Make public..."` and `"Make private"` as separate items.
  - **(b) One call to action in the empty and first-run states:** Hide the sidebar `"New entry"` button when there are no entries; the `EmptyState` carries the single primary button (the first-run guide lives inside it).
  - **(c) Save is never disabled for a hidden reason:** `Save draft` and `Save changes` stay enabled; with no changes they show `"No changes to save."` in the status line (visible on touch, not only on hover). Keep the disabled-reason rule for the controls that really must be disabled.

| Entry State | Primary & Secondary Action Bar | `More` Menu | Sidebar `"New entry"` |
| --- | --- | --- | --- |
| `first-run` / `empty` | None (`EmptyState` holds single primary CTA) | None | Hidden |
| `draft` / `error` | `Save draft` (enabled) + `Publish...` | `History`, `Delete entry...` | Visible |
| `unlisted` | `Save changes` (enabled) + `Visibility` menu (`Public`, `Unlisted` marked, `Private`) | `History`, `Delete entry...` | Visible |
| `public` | `Save changes` (enabled) + `Visibility` menu (`Public` marked, `Unlisted`, `Private`) | `History`, `Delete entry...` | Visible |
- **`D-FEEDBACK`:** Four message places, each with one job: (1) a page notice directly under the header for whole-page problems; (2) one action status line directly under the editor action bar; (3) field errors under the field; (4) confirmations in dialogs. No toast, no top banner. A new result replaces the previous one. Success results stay until the next action or navigation; errors persist and say how to fix; Undo appears inside the status line with a real countdown. Only these four places may carry `role=status` or `role=alert`; add a test that fails otherwise, and make message text come from the strings catalogue only.
- **`D-HELP`:** Instructional text appears only when needed: the first-run walkthrough once, with zero entries, shown as a stepper (steps separate), never again after dismissal (persisted); field help in a `"?"` popover or under the field on focus. No design-note, enum, HTTP or finding text in the UI. Counts, titles and plurals come from one helper; select options are never truncated.

#### Execution Order (`D-ORDER`)
- **`D-ORDER` (Monolith Split, Shared Building Blocks & Reference Editor Page Before Styling and Page Migration):** No real dependency blocks splitting the `renderer.ts` monolith, establishing shared building blocks, and building the Reference Editor Page before applying token tiers, copy catalogues, and CI guard rails to that real page. Therefore:
  1. In **WP-15**, execute in order: `WP-15.0` (DOM-id baseline & deferred migrations), `WP-15.1` (mechanical monolith split), `WP-15.2` (shared controls & form fields), `WP-15.3` (shared feedback & container components), then **`WP-15.7`** (the reference editor page, built to `D-WORKSPACE`, `D-EDITOR`, `D-FEEDBACK`, and `D-HELP`, with the interaction contract test across `draft`, `unlisted`, `public`, `error`, `empty`, and `first-run` states), and then **`WP-15.4` to `WP-15.6`** (token tiers, copy/help catalogues, and CI guard rails) applied to that real page.
  2. In **WP-16** (`Admin shell, entries and inbox`), **WP-17** (`Settings, maintenance and account`), and **WP-18** (`Authoring canvas and import`), migrate one self-contained admin page module at a time composing the shared building blocks; every finding remains mapped to a task with zero findings dropped.

## 7. Work packages for agent execution

### 7.0 Is the roadmap a set of phased work packages?

**No.** The P0/P1/P2 roadmap in §3 ranks problems by severity. An agent can’t execute a ranking without making decisions the ranking never records. The table shows what is missing.

| Property an agent needs | §3 roadmap | Work package (this section) |
| --- | --- | --- |
| Order and dependencies | Severity only; items 1 to 8 within a tier are not sequenced | Explicit dependency graph; one task at a time |
| Entry criteria | None | Baseline, decisions and prior gate that must hold before starting |
| Task granularity | Items of S to L effort, many spanning 3 to 10 files | One task = one pull request = one receipt |
| Acceptance | “Done when” in prose | Named Playwright tests and commands whose output proves it |
| Stop points | None | A gate closed by L at the end of every package |
| Handover | None | A handover file at every gate so a human can open a new session |
| Decisions | Hidden inside items | Numbered decisions with an owner and a default |
| Fit with repo rules | Not considered | Matches `execution-protocol.md`, `P001` (IAHP), `gates.json` and the register |

### 7.3 Standing instructions for every session

These apply to every package. They restate the repo’s rules only where an agent working from this plan could otherwise miss them.

1. **Entry.** Read the latest handover and `docs/plans/execution-protocol.md` and nothing else; run `pnpm handover:verify <H###>`; stop and report if any halt condition in the handover applies. Do not explore the repo. For WP-13 the “latest handover” is `H013`.
2. **Zero inference.** Cite exact paths, symbols and line anchors. Line numbers in this report are from the shipped zip and can drift; always re-locate by symbol or element ID and note any discrepancy in the receipt (section 1.0).
3. **One task at a time**, in the listed order; never reorder without a note and L’s sign-off.
4. **Verify first.** Each task opens with the repro: write the failing Playwright test that shows the defect, then fix it. Findings tagged **I** (inferred) in this report must be confirmed in a browser before any change; record the result.
5. **No new inline styles or hard-coded colours, sizes, copy or vendor names** in code written from WP-15 onward; use tokens, primitives and the catalogue. Until WP-15 lands, do not widen existing debt.
6. **Preserve test hooks.** Keep element `id`s and `data-*` attributes that conformance or e2e tests assert, or update those tests in the same pull request and say so.
7. **Evidence labelling:** `CI` for log blocks copied verbatim from the named job, `local output` otherwise, “computed from the above” for totals.
8. **Honesty.** Do not describe a behaviour as fixed unless a test in the receipt exercises it. Tag unfinished items `[partial]`, `[simulated]` or `[not-started]` as the repo does.
9. **Decisions.** Every decision is closed in §8. If a task meets a question §8 does not cover, choose the option that follows the spec and the principles in §6, record the choice and its reason in the receipt, and carry on; do not stop to ask. Spec first: a task that implements an amendment (A-01 to A-09, §5.4.2) or otherwise changes behaviour the spec describes edits the matching section of docs/spec/ in the same pull request.
10. **Exit.** At a gate, produce the closing receipt (gate summary and the fresh-clone command for L), wait for L’s sign-off, then write the handover and stop. Do no other work in that session.

**Start prompt (give this to every new session).** Take the template in `docs/templates/G001-handover-template.md`; its start prompt reads: *You are taking over the Living Portfolio implementation. Read `<path of the latest handover>`, then `docs/plans/execution-protocol.md`, and nothing else. Do not explore the repo. Run `pnpm handover:verify <H###>`. If any halt condition in section 8 applies, stop and report.* Each handover below lists the one **Immediate next action 1** the incoming agent should perform.
