## 1. Purpose and scope

Long agent conversations get expensive and unreliable: cost grows with context length, attention degrades, and settled reasoning is repeatedly re-derived. This protocol lets the project end a conversation at a **phase boundary** and start a fresh one with no loss of state, no re-exploration, and no regression into rejected approaches.

It governs three things only: how every document under `docs/` is identified, when a handover is required, and how a handover is written and consumed. It does not change the task workflow in `execution-protocol.md` (one task, one PR, one receipt).

## 2. Three artifact types that must not be confused

| Artifact | Cadence | Mutability | Purpose | Written from |
| --- | --- | --- | --- | --- |
| Task receipt `A###` | Every task | Immutable after merge; errata go in the next receipt section 7 | Evidence of what one task did | CI logs and the diff |
| Handover `H###` | Phase boundary only | Immutable after merge; a new `H` supersedes it | A derived snapshot a fresh session can resume from | Repo state, register, plan, latest receipts |
| Registry and index | Continuous | Generated by script | Unique ID and title for every document | `docs/doc-registry.json` |

Rules:
1. A handover never replaces a receipt, and a receipt never carries handover state beyond its section 9 decision.
2. A handover contains no history. History lives in git and in receipts. A handover contains only what the next session needs to act.
3. A handover duplicates no source of truth. It points to the register, the plan and the spec, and states only deltas and computed snapshots.

## 3. Document identity and naming (all files under `docs/`)

Every Markdown file under `docs/` has exactly one **ID** and one **title**.

| Class | Meaning | Directory | Filename | Mutable |
| --- | --- | --- | --- | --- |
| `A` | Task receipts and execution reports | `docs/execution-reports/` | `A###-<slug>.md` | No |
| `H` | Handover snapshots | `docs/handovers/` | `H###-<slug>.md` | No |
| `P` | Plans, protocols, decision records | `docs/plans/` or `docs/governance/` | `P###-<slug>.md` | Yes, with a revision history section |
| `G` | Guides, runbooks, references, templates | `docs/` or `docs/templates/` | `G###-<slug>.md` | Yes, with a revision history section |
| `L` | Legacy documents that predate this scheme | unchanged | unchanged | Frozen (reports, decision records) or Active (living plans, specs, guides, checklists) |

- **ID:** class letter plus three digits, allocated only by `pnpm docs:new <class> "<Title>"`. Never number by hand. Numbers are sequential per class with no gaps and no reuse.
- **Slug:** lowercase kebab-case, 3 to 8 words, at most 60 characters, describing scope (for example `wp1-publish-flow-preview-token`).
- **Title:** at most 80 characters, sentence case, states scope and purpose. No status words such as "final" or "update".
- **H1:** every non-legacy file begins with `# <ID> — <Title>`, and the filename and registry entry must match it.
- **Registry:** `docs/doc-registry.json` lists every document with `id`, `title`, `class`, `path`, `status` (`active`, `superseded`, `frozen`), `supersedes`, and for frozen documents `sha256`. `docs/INDEX.md` is generated from it and must not drift.
- **Legacy rule:** documents that exist when `PROC-1` lands are grandfathered and not renamed, because other documents link to them and closed audit folders are checksummed. Reports `A001` to `A012` keep their IDs as their legacy IDs and have status `frozen`. Every other legacy file gets an `L###` ID and a curated title **in the registry only**. Historical reports and decision records have status `frozen` (with an enforced `sha256`); living plans, protocols, specifications, guides, checklists, and changelogs have status `active` without a `sha256`.
- **Immutability:** `A` and `H` files never change after merge. Corrections go in a later `A` section 7 or in a superseding `H`.

## 4. When a handover is required

The decision is made at the end of every task receipt and recorded in its section 9 (format in section 10). The agent evaluates the rules in order and stops at the first match.

| Rule | Condition | Decision |
| --- | --- | --- |
| HO-R1 | A gate or phase just closed: L signed it off and the sign-off receipt is merged (end of WP-1, end of WP-2, and every later gate named in the plan) | REQUIRED |
| HO-R2 | L or the owner instructs a handover | REQUIRED |
| HO-R3 | Six or more receipts, or three or more work packages, since the last handover | RECOMMENDED |
| HO-R4 | Drift symptoms: re-deriving settled decisions, re-reading files only to re-orient, contradicting earlier receipts, or context-limit tool errors | RECOMMENDED |
| HO-R5 | None of the above | NOT REQUIRED |

Only L decides whether to act on RECOMMENDED. The agent cannot start a new conversation: it writes the handover and tells L to open a new session with the start prompt in the handover header.

**Clean-boundary preconditions** (all must hold before a handover is written; otherwise finish or abandon the work first):
1. The previous receipt is merged and its push runs on `main` are green.
2. There is no open PR except the handover's own docs-only PR.
3. The working tree is clean and no branch holds unmerged work that the handover would have to describe.
4. The CI baseline on `main` is the documented one (no unexplained failures).
5. There are no WIP commits. Handovers happen at boundaries, never mid-task.

## 5. Exit routine (outgoing session)

1. Verify the preconditions in section 4. If any fails, stop and report to L.
2. Run `git fetch` and record `git rev-parse origin/main` as the Evidence SHA. Record the three push run IDs for that SHA.
3. Run `pnpm docs:new H "<Title>"`. It creates `docs/handovers/H###-<slug>.md` from the template and registers it.
4. Fill each section by **derivation**, not narration: counts from CI logs and the register, the ledger from the plan, next tasks from the plan table. Carry forward from the previous `H` only decisions and pitfalls that are still valid. Delete resolved items. Do not edit the previous `H`.
5. Run `pnpm handover:check H###` until it passes.
6. Open a docs-only PR titled `docs: H### <title>`. Wait for CI green. Use **Rebase and merge**.
7. Print two lines: the handover path and the merge SHA, then the start prompt from the header.
8. Stop. Do no further work in this session.

## 6. Entry routine (incoming session)

1. Read, in this order and nothing else: the latest handover (the registry's highest `H` with status `active`), then `docs/plans/execution-protocol.md`. Do not explore the repository.
2. Run `pnpm handover:verify H###`. It checks that `origin/main` equals the Evidence SHA (or descends from it through docs-only commits), that `pnpm verify` passes, and that the baseline matches the handover's section 7.
3. **Halt conditions.** Stop, change nothing, and report to L if: `main` moved with non-docs commits; the baseline does not match; CI on `main` is red; a decision blocking Immediate Next Action 1 is still owned by L or the owner; a referenced path, SHA or command does not exist.
4. Record the intake in the first new receipt, subsection 1.0: handover ID, verification result, any discrepancy.
5. Execute Immediate Next Action 1. Ask a question only when a halt condition applies.

## 7. Authoring rules

- **Zero inference.** Every reference is an exact path (with line anchors where useful), symbol, finding ID, command, or SHA. No "the bug we discussed", no pronouns without antecedents. Item 1 of the next actions must be executable with no searching.
- **One home per fact.** If a fact lives in the register, plan, spec or a receipt, cite it; do not copy it.
- **Budget.** At most 300 lines and 32 KB; at most 7 hot files, 7 next actions, 10 decisions and 10 pitfalls. The check enforces these.
- **Evidence labels.** Counts and statuses are copied from a named CI run and labelled `CI` or `local`. Computed totals say "computed from the above".
- **Tags.** State claims carry `[implemented]`, `[partial]`, `[simulated]` or `[not-started]` as in the receipts.
- **Pending decisions** name an owner (`L` or `owner`) and what is blocked.
- **No secrets, no personal data.** Use handles and noreply addresses only, and never anything the hardcode and gitleaks gates would flag.

## 8. Roles and authority

| Role | Authority |
| --- | --- |
| A (implementer agent) | Implements tasks, writes receipts, proposes handovers, writes handovers when REQUIRED or when L accepts RECOMMENDED |
| L (lead reviewer) | Signs off gates, accepts or defers RECOMMENDED handovers, resolves pending decisions, starts the new session |
| Owner | Decides product, governance and account-level matters named in the handover |

A never edits an earlier receipt or handover, never changes a finding's status without meeting its criteria, and never reorders the task sequence without asking L.

## 9. What the handover covers (full structure in the template)

0. Header and start prompt. 1. Mission and constitution (digest plus pointers). 2. Source-of-truth map. 3. Phase ledger. 4. Active workspace. 5. Findings and backlog snapshot. 6. Decisions and pitfalls. 7. Verification harness. 8. Entry halt conditions and exit checklist.

## 10. Receipt structure and section 9 (every receipt from `A013` on)

Receipts keep the structure A010 to A012 already use, with one added section. `receipt-check` enforces it:

1. Scope. 2. CI Evidence (provenance, then one `Verbatim` block per job). 3. Tests Added and Count Change. 4. Files Touched. 5. Register and Backlog Changes. 6. Not Done (Tagged). 7. Changes to Earlier Reports. 8. Receipt Gate Self-Validation (the pasted output of `pnpm receipt:check A###`, which must end in the all-checks-passed line). 9. Handover Decision (new):

```markdown
## 9. Handover Decision
- Decision: NOT REQUIRED | RECOMMENDED | REQUIRED
- Rule(s): HO-R#
- Receipts since last handover: N (A### to A###); work packages since: N
- Clean-boundary preconditions: met | not met (list which)
- Next action: continue with task <ID> | task HO-<n> (write H###)
```

`receipt-check` fails if the section is missing or malformed.

## Appendix A. Seed pitfalls for the first handover

Carry these into `H001` until pruned:
1. Squash merge drops `Signed-off-by` trailers. Use **Rebase and merge** only.
2. Force-pushing rewritten history breaks DCO base resolution and Gitleaks range logic. Both now fall back to full history; do not rewrite history again without telling L.
3. vitest prints per-package summaries only. Label any total "computed from the above".
4. Receipt evidence must come from the cited CI job log. Local output is labelled local (A008 section 2.3 was wrong for this reason).
5. Never edit an earlier report. Put errata in the next receipt section 7.
6. Register mapping: UX-01 setup and sign-in; UX-02 admin fetches and CSRF; UX-03 redaction preview and publish gate; UX-05 deploy status; UX-09 admin operational screens.
